## 关键机理确认（代码级，src/cli/hook.mjs + src/core/runtime-manager.mjs）

1. **gate 只在 CAS MCP 工具调用时写 `current_sessions`**（`gateApplies` = gate 事件 + `casToolName()` 归一化后在 CAS 集合）；非 CAS 工具的 PreToolUse 只做 drain + veto，不写 gate。
2. **MCP 侧 session 身份唯一来源是 `current_sessions`**，dispatch 边界统一解析（`sessionContext`）。
3. **completion 的 session 归属在 spawn 时刻确定**（executions 行继承写入 completions），回流 claim 用 hook stdin 原样 session_id 匹配，**不读 current_sessions**——这是回流不串投的结构保证。

## 补充实测：活跃会话唯一性约束（gate 层运行互斥，2026-09-13 11:03）

用户在 TUI 会话 spawn 真实 Codex 任务（sleep 60 后返回），Web 会话（本验证者）实测：

| # | 场景 | 预期 | 实际 | 结果 |
|---|------|------|------|------|
| C1 | TUI 有 active execution 期间，Web 调任意 CAS 工具（codex_list_threads） | gate veto，工具不执行 | veto 文案 "CAS runtime … occupied by another Kimi session"，工具未到达 Runtime | ✅ |
| C2 | 对方 turn 结束后（active executions 清空）Web 重试 CAS 工具 | gate 懒切换（session_handoff）自动交接，调用成功 | list_threads 正常返回 19 线程，gate 切回 731af287 | ✅ |
| C3 | 对方两条 completion 的归属与投递 | 归属 TUI session、回流给 TUI，不串 Web | 两条均 session_9d289b57 + delivered，未流入本会话 | ✅ |

关键机理（sqlite-store.mjs `sessionGateTransition`）：互斥在 **Session Gate 层**而非线程层——(host, workspace) 内存在 active execution 且属于**另一** session 时，本会话所有 CAS 工具在 PreToolUse 阶段被 veto（`other_session_active`）；active 为 0 时按 `session_handoff` 原子建立/切换。即**运行期是 workspace 级会话互斥**（更早拦截，CAS 调用根本到不了 Runtime），空闲期才是会话间懒切换。之前"三层线程围栏"（thread_busy/session_conflict/thread_held）是 Runtime 层的第二道防线（gate 失效时兜底）。



1. **毫秒级 gate/dispatch 竞态窗口（理论）**：gate 切回自己之后、Runtime dispatch 读取 `current_sessions` 之前，若对方会话 gate 再切走，本次调用的归属会错到对方 session——completion 会回流给对方会话（不丢失，但串投）。规格将"同一 (host, workspace, session_id) 单活跃 interactive instance"列为产品约束，双会话并发 CAS 调用属约束边缘；单值 current_sessions 是该约束下的既定设计。登记为已知限制，不修复。
2. **运行中线程的 session 围栏（实测代码级核实，修正早前表述）**：turn 运行期间（active execution 存在）任何其他会话都抢不到——同 host 另一会话 `send` → `thread_busy`；`steer`/`interrupt` 有显式 session 围栏（`execution.sessionId !== session.sessionId` → `session_conflict` fail closed）；跨 host → `thread_held`。**idle 线程的 lazy takeover（turn 结束后同 host 任意会话可 send 接管）是设计语义**（线程资源回收再利用），非抢占。登记为设计事实。
3. TUI 会话空闲但 MCP 进程存活时 presence 持续刷新（heartbeat 与会话活动无关）——符合 Presence 设计（lease 表达"实例存活"）。
